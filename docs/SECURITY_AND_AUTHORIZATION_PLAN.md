### ENTERPRISE SECURITY ARCHITECTURE, AUTHENTICATION & RBAC SPECIFICATIONS

## 1. نموذج المصادقة وإدارة الجلسات (Authentication & Session Model)

* **المصادقة عبر ملفات تعريف الارتباط الآمنة (Secure HttpOnly Cookies):**
  * يتم تخزين رمز الجلسة / رمز الوصول داخل ملف تعريف ارتباط بخاصية `HttpOnly` و `SameSite=Lax` و `Secure` (في بيئات الإنتاج HTTPS).
  * هذا يمنع سرقة الجلسة نهائياً عبر هجمات Cross-Site Scripting (XSS) حيث تعجز برمجيات JavaScript الخبيثة عن قراءة الرمز.
* **تشفير كلمات المرور (Password Hashing):**
  * الاعتماد الحصري على خوارزمية **Argon2id** (أو bcrypt بمعامل تكلفة Cost Factor 12 كبديل مدعوم).
  * حظر تام لأي تخزين نصي لكلمات المرور، وفرض شروط تعقيد دنيا (10 أحرف كحد أدنى).
* **إلغاء الجلسات وإدارة دورة الحياة (Session Revocation):**
  * تخزين تجزئة الرموز المنعشة (Hashed tokens) في جدول `user_sessions`.
  * إمكانية قيام المستخدم أو مسؤول النظام بإلغاء جميع الجلسات النشطة فوراً بضغطة زر (Logout from all devices).

## 2. مصفوفة الصلاحيات متعددة المستويات (Role-Based Access Control - RBAC)

| الصلاحية / الدور | نطاق الصلاحية (Scope) | الوصف والأذونات |
|---|---|---|
| **Platform Operator (مشغل المنصة)** | مستوى النظام الشامل | مسؤول تقني في MIKHLAFI LABS. إدارة جميع المستأجرين، تفعيل التراخيص، مراقبة صحة النظام. غير متاح للعملاء إطلاقاً. |
| **Organization Owner (مالك المؤسسة)** | مستوى المؤسسة المستأجرة | كامل الصلاحيات داخل المؤسسة: الفوترة، إدارة الأعضاء، تعديل الفروع، تفعيل/تعطيل مصادر البيانات، حذف المؤسسة. |
| **Organization Admin (مدير المؤسسة)** | مستوى المؤسسة | إدارة أعضاء الفريق، ضبط مصادر البيانات، الاطلاع على سجلات التدقيق، ضبط إعدادات التحليلات. |
| **Manager (مدير تشغيلي / فرع)** | المؤسسة أو فرع محدد | إدارة العمليات الخاصة بفرعه، استعراض التحليلات والتقارير، اعتماد الإجراءات التشغيلية. |
| **Analyst (محلل بيانات / أعمال)** | مستوى المؤسسة أو الفرع | إنشاء التقارير، تشغيل تحليلات الشذوذ، استجواب المساعد الذكي، تصدير البيانات المصرح بها. |
| **Standard Member (عضو عادي)** | محدد بالمهام | استعراض المهام المسندة، قراءة لوحات القيادة العامة. |
| **Viewer (مشاهد فقط)** | قراءة فقط | استعراض المؤشرات والتقارير المعتمدة دون أي إمكانية للتعديل أو الحذف أو التصدير. |

## 3. ضمانات عزل المستأجرين (Tenant Isolation Enforcement)

1. **التحقق من السياق في السيرفر (Server-Side Context Validation):**
   * كل استدعاء للـ API يمر عبر Hook يقوم بـ:
     1. استخراج `user_id` من الجلسة الموثقة.
     2. استخراج `organization_id` الفعالة للمستخدم والتحقق من وجود عضوية نشطة له في جدول `memberships`.
     3. تثبيت `organization_id` في كائن الطلب `request.tenantId`.
2. **عزل الاستعلامات (Query Enforced Filtering):**
   * يتم تضمين شرط `WHERE organization_id = request.tenantId` تلقائياً في كل استعلام Drizzle ORM.
   * لا يمكن للمستخدم تمرير `organization_id` مختلف في المسار لتجاوز هذا التدقيق.
3. **حماية أمان الصفوف (PostgreSQL Row-Level Security):**
   * إضافة سياسات RLS على مستوى جداول البيانات المالية والمخاطر والمصادر كطبقة حماية ثانية تمنع تسرب أي بيانات خارج المؤسسة.

## 4. أمان استجواب الذكاء الاصطناعي (AI Data Access Security)

* **التحقق الأمني قبل بناء السياق (Pre-Prompt Context Filtering):**
  * قبل تزويد المساعد الذكي بأي بيانات للإجابة على استفسار المستخدم، يقوم الخادم باستعلام البيانات المصرح للمستخدم ومؤسسته بالوصول إليها حصراً.
  * لا يتم الاعتماد على تعليمات الذكاء الاصطناعي (Prompting Instructions) وحدها كحاجز أمني.
* **إخفاء وتطهير البيانات الحساسة (PII Sanitization):**
  * إزالة أي أرقام هوية أو أرقام بطاقات أو معلومات سرية قبل إرسال السياق لمحركات الذكاء الخارجي.

---

## 5. اختبارات الأمان والتدقيق المستمر (Security Auditing & Test Gates)

* **بوابات أمان إلزامية في CI/CD:**
  * اختبار محاولات الوصول غير المصرح عبر مستأجرين مختلفين (Tenant Cross-Access Test).
  * اختبار محاولة استدعاء مسارات `/admin/*` بمستخدم عادي والتحقق من استقبال رد `403 Forbidden`.
  * حظر تخزين أي مفاتيح API أو كلمات مرور داخل الكود البرمجي بواسطة أدوات مسح الأسرار الآلية.
