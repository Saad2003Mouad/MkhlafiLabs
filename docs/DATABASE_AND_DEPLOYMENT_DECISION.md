## 1. قرار قاعدة البيانات الأساسية: PostgreSQL 16+

* **القرار المعتمد:** اعتماد **PostgreSQL** كقاعدة البيانات الرئيسية والوحيدة لكافة العمليات والمعاملات متعددة المستأجرين.
* **الأسباب الفنية:**
  * ثبات عالي وقدرة على معالجة العمليات الحسابية المعقدة (ACID Transactions).
  * دعم ممتاز لتعدد المستأجرين عبر معايير الأمان على مستوى الصفوف (Row-Level Security - RLS).
  * حقول JSONB مرنة لتخزين البيانات غير الثابتة من مصادر التكامل الخارجية (Integrations metadata & dynamic fields).
  * استقلالية تامة وقابلية للتشغيل على أي خادم محلي (On-Premise) دون الحاجة لخدمات سحابية حصرية (مثل Supabase أو AWS RDS).

## 2. مقارنة واختيار الـ ORM: Drizzle ORM مقابل Prisma

| المعيار | Prisma ORM | Drizzle ORM (المعتمد) |
|---|---|---|
| **الأداء واستهلاك الموارد** | يستهلك ذاكرة أكبر بسبب محرك Rust الثنائي. | فائق السرعة وبدون أي عبء إضافي (Zero-runtime overhead). |
| **استعلامات SQL الناتجة** | طبقة تجريد عميقة قد تخفي تفاصيل الاستعلامات المعقدة. | تطابق مباشر مع أوامر SQL القياسية، شفافية تامة. |
| **دعم On-Premise في بيئات مقيدة** | قد يواجه مشاكل في التثبيت إذا كان الخادم يفتقر لترجمة حزم ثنائية محددة. | مبني بـ TypeScript خالص 100% دون أي ملفات ثنائية خارجية. |
| **التحكم بـ Migrations و RLS** | تحكم جيد ولكنه مقيد داخل مخطط `schema.prisma`. | كتابة وتوليد ملفات SQL صريحة قابلة للمراجعة والتدقيق الدقيق. |

* **القرار:** اعتماد **Drizzle ORM** مع محرك `drizzle-kit` لإدارة الـ Migrations.

## 3. نماذج النشر والتشغيل (Deployment Models)

### 3.1 النشر السحابي المدار (Managed Cloud Deployment)
* تشغيل حاويات Docker للمنصة والـ API عبر Kubernetes أو خوادم افتراضية خاصة (VPS) مثل Hetzner أو DigitalOcean أو AWS/GCP.
* استخدام قاعدة بيانات PostgreSQL مدارة مع نسخ احتياطي يومي آلي.
* طبقة موازنة أحمال وشهادات أمان SSL تلقائية عبر Caddy أو Nginx.

### 3.2 النشر الذاتي الداخلي لدى العميل (Enterprise On-Premises)
* توفير حزمة `docker-compose.yml` قائمة بذاتها تحتوي على:
  * واجهة التطبيق المترجمة (Static bundle).
  * خادم الـ API والخلفية (Fastify Server).
  * قاعدة بيانات PostgreSQL مع الـ Extensions المطلوبة.
  * خادم Redis لجلسات العمل والمهام المؤجلة.
* دليل تثبيت تفصيلي خطوة بخطوة في `docs/DEPLOYMENT.md` يتيح لمهندسي العميل تثبيت النظام في غضون 15 دقيقة دون مساعدة خارجية.

## 4. حدود التشغيل بدون إنترنت (Offline Reality vs Dependencies)

لتفادي الوعود غير الدقيقة، تم توثيق ما يمكن وما لا يمكن تشغيله بدون اتصال بالإنترنت (Offline Mode):

| الخاصية / الوظيفة | هل تعمل محلياً بدون إنترنت؟ | البديل المحلي الموثق (Offline Alternative) |
|---|---|---|
| **تسجيل الدخول وإدارة المؤسسات والفرق** | ✅ نعم بالكامل | مصادقة محلية عبر قاعدة بيانات PostgreSQL الداخلية. |
| **الذكاء المالي والتحليلات وكشف الشذوذ** | ✅ نعم بالكامل | خوارزميات إحصائية ومعادلات مبنية داخل السيرفر تعمل محلياً. |
| **مؤشرات الأداء ولوحة القيادة والتقارير** | ✅ نعم بالكامل | استعلامات SQL ومعالجات بيانات تعمل داخل الخادم المحلي. |
| **المساعد الذكي (AI Assistant)** | ⚠️ مشروط | يعمل محلياً إذا رُبط بمحرك ذكاء محلي مثل **Ollama** أو نماذج مفتوحة المصدر (Llama 3 / Mistral) داخل شبكة العميل. يتطلب إنترنت إذا رُبط بـ Gemini Cloud. |
| **إرسال رسائل البريد الإلكتروني للتفعيل** | ❌ يتطلب إنترنت أو SMTP محلي | يتطلب وجود خادم بريد محلي (Local SMTP Server) داخل شبكة العميل، أو توليد روابط التفعيل يدوياً بواسطة مسؤول النظام. |
| **الربط مع بوابات الدفع الإلكتروني السحابية** | ❌ يتطلب إنترنت | في بيئات النشر الداخلي، يتم تفعيل الدفع بالتحويل البنكي أو الفواتير اليدوية بدلاً من بوابات الدفع الفورية. |

## 5. خطة النسخ الاحتياطي والاستعادة (Backup & Disaster Recovery)

1. **النسخ الاحتياطي اليومي:**
   * سكربت آلي يومي ينفذ أمر `pg_dump` مشفر بمفتاح محلي ويحفظه في مسار آمن منفصل.
2. **اختبار الاستعادة الدورية:**
   * اختبار صحة استعادة البيانات واستيرادها دورياً للتأكد من سلامة ملفات النسخ وخلوها من التلف.
3. **التراجع عن الـ Migrations:**
   * كتابة ملفات التراجع (Rollback scripts) لكل تعديل يطرأ على جداول قاعدة البيانات.
