# MIKHLAFI LABS — قرارات معمارية الواجهة الأمامية
### FRONTEND ARCHITECTURE & MIGRATION STRATEGY
**Version:** 1.0.0 | React + TypeScript Mandatory Standard  

---

## 1. لماذا React و TypeScript إلزاميان من البداية؟ (Why React + TypeScript Now?)

1. **التعقيد المؤسسي وتفادي الكود الهش (Enterprise Scale vs Fragility):**
   * الواجهة السابقة المكتوبة بـ Vanilla JavaScript في ملفات ضخمة (مثل `platform.js` بحجم 46KB و `data.js` بحجم 44KB) تؤدي إلى صعوبة إدارة الحالة (State Management)، غياب التحقق من أنواع البيانات (Type Safety)، وتراكم أخطاء وقت التشغيل (Runtime Errors) التي يصعب اكتشافها مبكراً.
   * وضع TypeScript الصارم (`strict: true`) يضمن وجود عقود بيانات موثوقة (Data Contracts) بين الواجهة والخادم، مما يمنع حدوث أخطاء مثل `Cannot read property of undefined` في مؤشرات الأداء الحساسة.
2. **منع إعادة كتابة الكود لاحقاً (No Deferral to Phase 3):**
   * تأجيل الترحيل إلى مرحلة لاحقة كان سيعني إهدار الجهد في بناء واجهات مؤقتة يتم التخلص منها لاحقاً. البدء بـ React و TypeScript يضمن أن كل مكون يُبنى اليوم هو استثمار دائم للإنتاج.
3. **بنية المكونات المعيارية وقابلية الاختبار:**
   * فصل الشاشات إلى مكونات وظيفية دقيقة يتيح اختبارها آلياً، إعادة استخدامها عبر مختلف وحدات الذكاء، وتوفير شاشات تحميل (Skeleton states) وشاشات أخطاء متناسقة وموثوقة.

## 2. نظام البناء وإدارة المسارات (Build System & Routing)

* **نظام البناء (Build Tool):** **Vite**
  * سرعة فائقة في التطوير المحلي ومعالجة الوحدات الفورية (ES Modules).
  * تكوين مدمج وسهل لمعالجة CSS Modules و PostCSS ونظام المتغيرات.
* **إدارة المسارات (Routing):** **React Router v6/v7**
  * دعم التجزئة الهرمية للمسارات (Nested Layouts) لعزل تخطيط الموقع العام عن تخطيط لوحة التحكم وعن لوحة الإدارة.
  * تحميل تدريجي للمسارات الكبيرة (Route-based Code Splitting عبر `React.lazy` و `Suspense`).
  * مسارات محمية ومراقبة صلاحيات (Protected Route Wrappers).

## 3. إدارة الحالة وطبقة الاتصال بالخادم (State & API Strategy)

```
[مكونات الصفحة Page Components]
           │
           ▼
[خطافات البيانات Data Hooks: useDashboardData, useIntelligenceModule]
           │
           ▼
[طبقة العميل الموحد Typed API Client (Fetch + Zod validation)]
           │
           ▼
[الخادم الخلفي / أو وضع العرض التجريبي المدار Demo Provider]
```

1. **حالة الخادم (Server State):**
   * استخدام خطافات مخصصة مبنية على معايير `TanStack Query` (React Query) أو إدارة مدمجة للتخزين المؤقت وإعادة المحاولة التلقائية ومعالجة حالات التحميل والأخطاء.
2. **حالة واجهة المستخدم (UI State):**
   * إدارة تفضيلات المظهر (Dark/Light)، اللغة (AR/EN)، وطي/فتح القائمة الجانبية عبر React Context API خفيف ومنظم.
3. **حالة النماذج (Form State):**
   * اعتماد **React Hook Form** مع **Zod** للتحقق من صحة المدخلات في الواجهة قبل إرسالها إلى الخادم.
4. **عميل الـ API الموحد (Typed API Client):**
   * تجميع كافة استدعاءات الشبكة في عميل موحد يتولى:
     * إضافة بيانات المصادقة بأمان (Credentials / HttpOnly cookies).
     * معالجة الأخطاء القياسية (401 Unauthorized -> توجيه للدخول، 403 Forbidden -> عرض شاشة عدم الصلاحية).
     * دعم وضع التجربة (Demo Provider) الذي يعيد بيانات استرشادية دون الاتصال بالخادم، مع تمييزها صراحة للمستخدم.

## 4. استراتيجية الترحيل الآمن وعدم كسر التجربة الحالية (Safe Migration Strategy)

| المرحلة | الإجراء المتبع | حالة التطبيق الحالي |
|---|---|---|
| **المرحلة 0** | تشغيل واجهة React التجريبية في مسار مستقل ومنفصل مع الحفاظ على خادم `server.js` الأصلي وشاشة `index.html` دون أي تعديل يكسرها. | العرض الأصلي متاح 100% على `localhost:3000`. |
| **المرحلة 1** | بناء قوالب الصفحات الرئيسية ومكونات نظام التصميم واختبار تجربة RTL/LTR والوضع الليلي في React. | العرض التجريبي الأصلي يعمل بجانب الأساس الجديد. |
| **المرحلة 2** | ربط تطبيق React بنقاط الـ API الحقيقية للتوثيق والمؤسسات. | استبدال تدريجي للمسارات. |
| **المرحلة 3 وما بعدها** | الترحيل الكامل لجميع شاشات التحليل واستبدال شاشات Vanilla JS نهائياً بعد إثبات الجاهزية والاستقرار الكامل. | إحالة الكود القديم للتقاعد بأمان تام. |
